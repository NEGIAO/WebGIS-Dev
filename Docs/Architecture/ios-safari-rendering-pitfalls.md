# iOS Safari 旋转图层黑块：成因、触发条件与规避规约

> **定位**：跨模块的渲染约束文档。凡是要在「持续旋转的装饰层」上叠加**新图层**（点、光斑、描边、文本、图片）时，先读本篇。
> **来源**：2026-11-02 首屏三环纹样黑块的完整排查（9 轮真机二分），日志见 [`LLM_record/26-11/2026-11-02/2026-11-02-ios-ring-black-fix.md`](../LLM_record/26-11/2026-11-02/2026-11-02-ios-ring-black-fix.md)。
> **结论强度**：现象与触发条件为**真机实测**；底层机制为**推断**（无 WebKit 源码级证据），已在下文标注。

---

## 一、一句话结论

在 iOS Safari 里，**一个「覆盖整块区域、绕自身圆心旋转、且带圆角裁剪」的独立图层**，很可能被整块渲染成黑色。它不是某个 CSS 属性写错了，而是这类图层在当前 WebKit 合成器里画不出来。

> 换句话说：**不是"某个属性有毒"，而是"某种图层结构在这个环境下不可用"。**

## 二、现象

| 项 | 表现 |
|---|---|
| 平台 | iOS Safari（真机 iPhone，iOS 16+）；桌面 Chrome / Edge / Firefox 全部正常 |
| 外观 | 旋转装饰层所在区域整块变黑（不是缺图、不是透明、不是色偏） |
| 持续性 | 稳定复现，不是首帧闪烁；与网络、缓存、图片是否加载完无关 |
| 影响范围 | 仅视觉；无 JS 报错、无布局变化、无控制台警告 |

关键特征：**黑的是"层"，不是"图"**。换图源、换图片格式、换承载元素都不改变结果。

## 三、触发条件

本仓库实测归纳为**三个条件同时成立**：

1. **是一个独立图层** —— 有 `transform` 动画，或 `opacity < 1`、`mask`、`filter` 等会强制建层的属性；
2. **绕自身圆心做完整旋转** —— `transform: rotate()` 连续动画，圆心落在图层几何中心；
3. **图层覆盖整块区域且需要圆角裁剪** —— 图层尺寸等于/接近容器，并有 `border-radius: 50%`（或等价的圆形裁剪）。

三条里去掉任意一条，黑块消失。实测对照：

| 配置 | 条件 1 | 条件 2 | 条件 3 | 结果 |
|---|---|---|---|---|
| 环本体（`border: 1px dashed` + `rotate`） | ✅ | ✅ | ✅（圆形边框） | **正常** ← 反例，见下 |
| 纹样 `::before`（背景图 + 父级 `rotate`） | ✅ | 继承父级旋转 | ✅ | **正常** |
| 公转点 `::after`（整环透明层 + 渐变 + 圆角 + 自身 `rotate`） | ✅ | ✅ | ✅ | **黑** |
| 公转点拆成兄弟节点（只留自身 `rotate`） | ✅ | ✅ | ✅ | **仍黑** |

上表的两个"正常"说明条件写法还需收紧，真实判据更接近：**一个"没有实体内容（只有渐变/半透明）、却被圆角裁剪、且绕圆心转"的空图层**。

- 环本体有**实体边框**，绘制内容在图层边缘，不靠整块裁剪；
- 纹样层有**位图内容**，且旋转是继承父级（整棵子树一次变换）；
- 公转点是**纯渐变 + 圆形裁剪 + 整块透明**——三条都占，于是画不出来。

> ⚠️ 这条判据是**基于 9 次对照的归纳**，不是 WebKit 官方文档。遇到新组合时，按第 8 节的二分法实测，不要直接套结论。

## 四、为什么容易误判成"某个属性"

本次排查的前 7 轮全部落在"属性级"假设上，全部无效：

| # | 改的是什么 | 结果 |
|---|---|---|
| 1 | 纹样从 `mask-image` 换成 `background-image` | 仍黑 |
| 2 | 去掉 `opacity`，压淡改用背景叠色 | 仍黑 |
| 3 | 伪元素背景换成真实 `<img>` | 仍黑 |
| 4 | 移动端只保留一张 PNG（减数量） | 仍黑 |
| 5 | 让纹样静止（停旋转） | 仍黑 |
| 6 | 环线置透明（保留元素与动画） | **正常** |
| 7 | 加回 `1px dashed` 环线 | **正常** |
| 8 | 加回两个公转点 | **又黑** |
| 9 | 点从 `::after` 改成兄弟节点、只留一层旋转 | **仍黑** |

教训：

- 第 1–5 轮改的都是**"已经被证明安全"的图层**，所以无论怎么改都不会有变化——排查方向从一开始就偏了；
- 第 6–7 轮的正确做法是**做减法而不是换写法**：把可疑图层整块拿掉，看现象是否消失；
- 第 9 轮证伪了"层数叠加"的假说：**降层数不解决问题，换结构才解决**。

## 五、机制（推断，非实测）

iOS 上的 WebKit 用 CoreAnimation 合成。当一个图层既需要「圆角裁剪」又需要「持续变换」时，合成器会为它分配一块后备存储（backing store）并按帧重绘；纯渐变 + 整块透明 + 圆形裁剪的组合会让这块存储在某些版本上**保持未初始化状态**——未初始化的位图默认是黑色，于是就"整块黑"。

支持这个推断的旁证：**黑块区域边缘恰好是圆形裁剪的形状**，而不是图片本身的形状；且换成有位图内容或实体边框的图层就不再黑。

## 六、规避规约（写动效前的检查清单）

新增任何"跟着环转/自己转"的装饰层时，逐条确认：

1. **不要给"纯装饰图层"同时上三件套**：整块透明 + 圆形/异形裁剪 + 绕圆心旋转。要么给实体内容（边框、位图），要么去掉裁剪，要么别让它转。
2. **旋转优先挂在"有实体内容"的元素上**：边框、图片、文字都可以；空图层不行。
3. **一个图层只承担一层旋转**。多层叠加虽不是本例的根因，但同样是高风险的合成路径，没必要试。
4. **需要"点绕圈"这类效果**，改用不依赖 CSS 图层旋转的画法：
   - SVG `<circle>` + `stroke-dashoffset` 动画（推荐，GPU 友好、无裁剪层）；
   - `<canvas>` 逐帧绘制（最可控，但要走 rAF，注意省电）；
   - 或用**位置动画**（`offset-path` / `translate` 关键帧）代替旋转。
5. **必须用 CSS 旋转时**，给图层加实体内容（哪怕是一条 `border`），并避免 `border-radius` 裁剪整块透明面。
6. **测试要求**：这类改动**必须真机（iOS Safari）复验**，F12 的设备模拟不还原合成行为。凡涉及 iOS 的视觉缺陷，禁止只凭桌面浏览器下结论。

## 八、真机排查手册（下次 5 分钟定位）

不要一上来改属性，按"整块拿掉"的顺序做减法：

1. **列出该区域所有图层**（`transform` / `opacity` / `mask` / `filter` / 伪元素 / 子元素）；
2. **一次只删一个**，每删一次在 iPhone 上看一眼——删到不黑为止，最后删掉的那个就是嫌疑层；
3. 找到嫌疑层后，**先试"换成实体内容"**（加边框 / 换位图 / 去掉圆角裁剪），再考虑换绘制体系；
4. 若一次删多个（比如本次第 6 步同时删了边框和点），记得**逐项加回来验证**，否则无法定位；
5. 结论回填本文档第七节，并检查是否有同构写法。
