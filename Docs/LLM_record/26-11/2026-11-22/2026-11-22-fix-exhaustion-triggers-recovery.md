## 问题分析

### 核心症状（HF 生产日志 16:41:36–37）

撕裂爆发（3 连重试全部失败）→ `GET /api/statistics/center` **500** → 14 秒后自愈（200）。**全程无 rebuild**——恢复分支没有被触发。

### 根本原因（防线缺口）

V3.7.9 的设计假设「重试耗尽 → 下一次借出探测路由到恢复分支」只对**页头级**损坏成立：借出探测 `SELECT 1` 只触页头，**页级损坏时探测仍通过** → `_auth_storage_ready` 保持 True → 快路径直接复用旧连接 → 恢复分支永远不会被触发 → 只能干等 FS 缓存自愈（本次 ~14s）。**若损坏是持久性的（真文件损伤），统计页将持续 500 直到手动重启**——这正是 V3.7.9 日志遗留项 1 预言的场景，本次生产实证。

### 事件还原（16:41 证据链）

1. 16:41:36 三连重试失败（`system_config`/center 域查询，malformed）
2. 16:41:37,159 500（`/api/statistics/center`）
3. 16:41:37,175 `realtime` 200（不同页，未受损）——撕裂仅命中特定页
4. 16:41:51 `center` 200——FS 缓存级自愈（~14s），文件本体未损
5. **16:42:08 用户更新 `agent_api_key`** → 16:42:21 阿里云 models 200 → **后端代理通道恢复**（16:36–16:38 的 5 连 401 为用户更新 key 前测试代理模式，被 V3.7.12 候选失败日志如实捕获）

### 解决方案

执行期损坏重试耗尽时（仅损坏类错误），在连接 execute 的异常路径**复位 `_auth_storage_ready = False`** → 下一次借出跳过快路径 → 恢复分支以**新鲜句柄** quick_check：文件真损坏 → 重建；瞬态 → 仅换新句柄即恢复（新鲜句柄不依赖 FS 缓存过期）。复用全部既有机制，~10 行。

## 影响范围

全部 `get_auth_db_connection()` 调用方；行为仅在「损坏类错误重试耗尽」时变化（多一次全进程换句柄/rebuild）。瞬态场景代价 = 一次 `_ensure_schema` 幂等校验 + 代际推进（全线程换新句柄，µs 级）；持久场景 = 既有 archive+rebuild 保全流程。
