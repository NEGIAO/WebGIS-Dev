## 一、问题分析

### 核心症状

用户截图反馈：Agent 回答的表格单元格中，`** favorable**` 显示为字面文本，未渲染为加粗。

### 根本原因

不是表格渲染器或 DOMPurify 的问题——自定义 renderer 只覆写了 `code()`，表格走 `marked` 默认 GFM 解析。

实测 `marked.parse()`：

| 输入 | 输出 |
|---|---|
| `\| 正北 \| ** favorable**: 测试 \|` | `<td>** favorable**: 测试</td>`（未加粗） |
| `\| 正北 \| **favorable**: 测试 \|` | `<td><strong>favorable</strong>: 测试</td>`（正常） |

CommonMark 规定 `**` 后紧跟空白**不构成强调**。LLM 在中英混排时高频产出 `** word**`（星号内侧多空格）这种非规范格式，`marked` 严格按规范解析，故原样显示。

### 受影响模块

| 模块 | 影响 |
|---|---|
| `useMarkdownRenderer.ts` | 缺 LLM 输出瑕疵的容错归一化 |

### 方案对比

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 换/配置 markdown 库放宽语法 | 一劳永逸 | marked 无此选项；换库影响面大 | 拒绝 |
| B. 让 LLM 输出规范格式（改提示词） | 治本 | 不可靠，模型仍会犯错；历史消息已存在 | 拒绝 |
| C. 解析前归一化（选定） | 精准、局部、零依赖 | 需防误伤代码块与公式 | 采用 |

## 二、修改内容

`useMarkdownRenderer.ts` 新增 `normalizeEmphasisSpacing(text)`：

1. **保护代码块**：fenced（` ```...``` `）与 inline（`` `...` ``）先提取为占位符，避免误伤 Python 幂运算 `a ** b` 这类代码内容；
2. **归一化成对加粗内侧空白**：
   - `\*\*[ \t]+([^*\n]+?)\*\*` → `**$1**`（处理 `** favorable**`）；
   - `\*\*([^*\n]+?)[ \t]+\*\*` → `**$1**`（处理 `**favorable **`）；
   - 内容不含 `*` 与换行，避免跨行误匹配及 `a * b * c` 误伤；
3. **还原代码块**。

调用位置：`extractMathExpressions()` 之后、`marked.parse()` 之前。数学公式此时已是纯字母数字占位符，天然不受影响。

`renderAnswerHtml` 与 `renderThinkHtml` 两条路径均已接入。

DOMPurify 消毒、KaTeX 回代、代码块高亮的既有顺序零改动。

## 四、流式答复左边界修复（V3.7.25）

### 核心症状

用户截图反馈流式回答中 `基于九星中的**”巨“卦，中心点位于江苏省南京市栖霞区仙林街道南京大学仙林校区**，分析半径约为2000 米` 的加粗未渲染，并指出"因为是 stream 流式传输"。

### 根本原因

逐帧实测 `marked.parse()` 结果：

| 输入 | 结果 |
|---|---|
| `**”巨“卦，中心点位于…校区**`（独立成句） | ✅ 加粗 |
| `基于九星中的**”巨“卦，中心点位于…校区**` | ❌ 未加粗 |
| `基于九星中的 **”巨“卦，中心点位于…校区**`（前面加空格） | ✅ 加粗 |

这**不是 V3.7.24 修的内侧空格问题**，而是第二类瑕疵：**CommonMark 规定强调开始符左边界不能是 word character，CJK 汉字同样受此限制**。`中的**` 紧贴"中"字，被判为字面量。LLM 中英混排时高频产出。

流式时序经核查**不是问题**：`ChatMessageList.vue` 用 `v-html="renderAnswer(msg.content)"` 绑定响应式 content，`onDelta` 每帧直接赋值新累积文本；`cachedRender` 以完整 content 为 key，流式每帧内容不同不会命中旧缓存。

### 修复

`normalizeEmphasisSpacing` 扩展 2b 步：

```ts
result = result.replace(/([\u4e00-\u9fff\w])(\*\*[^*\n]+?\*\*)/g, '$1 $2');
```

对**成对且闭合**的 `词**内容**` 在词字符后补一个空格。

关键安全设计：**只匹配闭合对**——流式逐字渲染中间态的单个未闭合 `**`（如 `中的**”巨“卦`）不会被改动，避免中间态文本漂移；闭合那一刻才补空格并渲染，属正常的流式 markdown 现象。代码块与数学占位符保护沿用 V3.7.24。

### 验证结果

10 项边界用例全过：截图原话、上一轮内侧空格瑕疵、英文词左边界、正常加粗不变、已空格不变、**流式半截不改**、fenced/inline code 保护、数学占位符保护、普通星号不误伤。

- `npm run typecheck`：✅ 0 错误
- Git 写操作：零

### 遗留与风险

- 流式期间未闭合的 `**` 会短暂显示字面星号，闭合后变加粗（闪烁）。这是流式 markdown 的固有现象，非 bug；若用户要求消除，可在流式期对未闭合 `**` 做视觉遮蔽，属优化范畴。
- 斜体 `*` 的同类左边界瑕疵未覆盖，如需可套用同一模式。

## 五、跨对误配修复（V3.7.26）

### 核心症状

用户截图反馈风水答复中 `**吉凶取向：**`、`**趋吉避凶：**`、`**“汇聚智慧”**` 均显示为字面星号。

### 根本原因

这是**V3.7.24/25 修复自身引入的回归**。调试发现原始文本 `**吉凶取向：** 在此…，**倾向于吉象**。` 经 `marked.parse()` 本就渲染正确；但归一化后变成 `**吉凶取向：**在此…，<strong>倾向于吉象</strong>`——第一处加粗被破坏。

根因：两条贪婪正则 `\*\*[ \t]+([^*\n]+?)\*\*` 与 `\*\*([^*\n]+?)[ \t]+\*\*` 无法判断某个 `**` 是开始符还是结束符。第一条把 `**吉凶取向：** 在此…**倾向于吉象**` 中**前一对的闭符**与**后一对的开符**误配成一对（中间内容 ` 宜将风水重点放在` 不含 `*`，长度不限），吃掉空格后破坏了前一对的闭合。

同理 V3.7.25 的左边界正则也会跨对匹配。这类"用正则猜配对"的方案本质上不可靠。

### 修复

重写 `normalizeEmphasisSpacing` 为**逐行状态机**：

1. 代码块保护（fenced + inline）沿用；
2. 逐行扫描所有 `**` 的位置，按出现顺序**两两配对**（0↔1、2↔3…），配对确定性，不跨对；
3. 在每一对内部：去内侧空格；依据该对**确切的**左邻字符与右邻字符决定是否补空格（同时处理左边界与右边界）；
4. 奇数个 `**` 时最后一个视为流式未闭合，跳过不处理；
5. 还原代码块。

右边界处理解决「放在**“汇聚智慧”**而非**“征服自然”**」——闭符右侧紧贴"而"字同样导致 CommonMark 配对失败，补空格后两个加粗都正常。
