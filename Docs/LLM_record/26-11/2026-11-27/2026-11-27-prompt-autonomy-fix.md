## 一、问题分析

### 核心症状

用户点击建议词「分析当前视图范围的风水条件」，模型不调用 `enable_compass`，反而回复「请先使用 search_and_zoom 工具定位一个具体地点…请告诉我您希望分析的地点（地名/地址/POI）以及一个分析半径（米）」。

### 根本原因

V3.7.19 工具 description 压缩的副作用，叠加 V3.7.17 System Prompt 瘦身时留下的机械化写法：

1. `enable_compass` 原 description 含「用于『分析当前或已定位范围风水条件』类请求」，压缩时被删，只剩「分析指定地点必须先 search_and_zoom 定位」——模型据此认为所有风水请求都需先定位；
2. `radiusMeters` 被写成「必须显式传入」，模型理解为「信息不足，需向用户索要」；
3. System Prompt「关键规则」用「先…下一轮…不得只定位后停止」写死步骤，挤占模型自主判断空间。

用户明确指出：「提示词改得太垃圾，都不让 agent 发挥自己的能力和推理了，让他自行判断」——这是对设计方向的批评，不是单点 bug。

|---|---|

## 二、修改内容

### 1. `enable_compass` description

恢复场景判断语义，明确两种情形由模型自行区分：
- 「分析当前视图范围」→ 直接用当前中心，无须再问地点；
- 「分析指定地点」→ 先 search_and_zoom 定位（仅 geocode 不够）。

半径改为「由你自行判断」：优先 `compassRadiusHintMeters`，缺失时按 zoom/cameraHeight 估算，**不要反问用户、不要沿用过小默认值**。

### 2. `radiusMeters` 参数描述

「必须显式传入」→「由你根据上下文自行决定并填入…不要询问用户」。

### 3. System Prompt

`## 关键规则`（写死步骤）→ `## 能力边界（自行判断怎么用）`：
- 开场「工具签名以 tools 为准，按用户意图自由组合与分轮，不必套固定流程」；
- 各能力只描述工具能做什么、参数怎么选，不再规定「先 X 下一轮 Y 不得 Z」；
- 保留真正不可违反的硬约束：删除不可撤销需报告、失败如实转述 code/message、额度耗尽立即停止、最终答复给具体结果。

## 四、罗盘协议恢复（V3.7.23）

### 核心症状

用户明确指出：「罗盘的预设命令是一个连串的、复杂的分析过程——首先是 agent 启动罗盘，然后让用户点击方位，自动进行分析」，V3.7.22 的改动让这条链路用不成了。

### 根本原因

V3.7.22 把罗盘协议压成一句「点击会自动回传再分析」，丢掉了三个关键环节：

1. **启用轮止步点**：卦象未选时无分析对象，启用后应提示用户点卦象即结束本轮；
2. **回传轮的性质**：平台自动投递的是带宫位名/坐标/半径的**知识解答类**新提问（`PalaceExplanationPanel.buildAgentQuestion` → `chatStore.requestPrompt` → ChatPanelContent 消费），模板明确要求直接作答、仅必要时调 reverse_geocode；
3. **内置咨询边界**：宫位/卦象/山向/星宿释义属平台功能咨询，不能拒绝；半径映射表防小比例尺罗盘不可见；堪舆引用需严谨不编造。

深层原因是把两类内容混为一谈：**交互协议是客观平台机制**（模型无法自行发明"用户点击会回传"），**决策方式才可交给模型判断**。前者必须写清，后者才该放手。

### 修复

System Prompt 新增独立段落「## 风水罗盘交互协议（平台内置机制，非可选流程）」，分两轮写清：

- **第一轮（启用）**：当前范围直接启用 / 指定地点先 search_and_zoom；半径按 compassRadiusHintMeters 或 OL/Cesium 映射表自主估算、不反问用户；启用后提示点卦象，**本轮到此为止**。
- **第二轮（回传）**：识别为自动回传的宫位提问，直接结合地理环境与宫位含义作答；**不要重复启用罗盘**；仅必要时 reverse_geocode；内置咨询不拒绝；堪舆引用有据可循、流派差异如实说明、不编造。

`enable_compass` 工具 description 同步写明两轮边界（"本轮到此为止…届时直接分析作答，不要重复启用本工具"）。
