## 1. 问题分析

### 核心症状

`Docs/Force_command.md`（59 行）作为 Agent 唯一行为准则，长期存在**"规范说 A、仓库实际是 B"**的脱节，导致每次会话交接时 Agent 依据错误规则施工，或因规则自相矛盾而各自发挥。

### 根本原因

规范自 3.0 启用后，仓库经历了**文档原子化重构**（版本记录拆出 CHANGELOG、目录树拆出三个 structure 文件）与**门禁脚本引入**（CheckStructureTree / CheckConfigRegistry），但规范文本未跟随演进，形成四处硬性脱节：

| # | 规范原文 | 仓库实际 | 后果 |
|---|---|---|---|
| 1 | 第 5 条"必须同步更新**三个 README** 中的文件结构树" | 三个 README 均 0 处树（`grep -c "├──"` = 0/0/0），权威树在 `Docs/Guide/*-structure.md` | Agent 找不到树可改；同条第 21 行又写"唯一的文件树记录是 project-structure.md"，**同一条内部打架** |
| 2 | 日志路径 `/Docs/LLM_record/yy-mm-dd/` | 实际两级 `26-07/26-07-01/`，且已漂移出三种写法：`26-05/26-05-01/`、`26-06/06-27/`（缺年）、`26-07-26/`（平铺 44 文件） | 每个会话按自己的理解建目录，归档持续劣化 |
| 3 | 全文未提门禁脚本 | 仓库根有 `CheckStructureTree.py` / `CheckConfigRegistry.py`，`LocalDev.bat` 第 89–91 行已接入 | Agent 完全不知道要跑，结构树漂移与配置未登记无人拦截 |
| 4 | 第 56 条"相同的日期，大版本只能更新一次" | 同日实际 V3.4.38 → 3.4.41 连续递增 | 规则失效且与现状矛盾 |

### 深层原因（本次重点解决）

除上述"内容过期"外，原规范的**结构**也不适配 LLM 协作：

- **无任务分级**：字面要求"任何增删改都要全套日志 + 版本号"，改一个 typo 也要走完整流程 → 实际结果是 Agent 敷衍或直接跳过，规范权威性被自身的不合理严苛消解。
- **无冲突裁决**：规范之间、规范与代码现状矛盾时没有处置规则 → Agent 自行选一种解释继续施工，错误被固化。
- **无失效边界**：未针对 LLM 典型失效模式（臆造 API/路径、谎报"已测试"、静默跳过做不到的事）设防。
- **无交接产物**：规范名为"确保顺利交接"，却没有规定会话结束时该输出什么 → 下个会话仍需重新摸索。

### 受影响模块

纯文档层：`Docs/Force_command.md`、`Docs/Guide/dev-conventions.md`。**零代码改动，零运行时影响。**

## 2. 解决方案

### 方案选型

| 方案 | 评估 | 结论 |
|---|---|---|
| A. 局部打补丁（改掉 4 处过期表述） | 成本最低，但结构性缺陷（无分级/无裁决/无交接块）仍在 | 否决 |
| B. 新建根 `CLAUDE.md` 自动加载入口 + 精简 Force_command | 可解决"每次需手动引用文档"，但用户明确选择不新增文件 | 用户否决 |
| C. **原地重写 Force_command.md 为四段式（边界 / 流程 / DoD / 交接）** | 一次性修正内容脱节 + 结构缺陷，保持单文件不新增 | **采用** |

### 实施内容

**① `Docs/Force_command.md` 重写**（59 → 210 行，十节结构）

| 节 | 内容 | 解决的问题 |
|---|---|---|
| 0 | 冲突裁决优先级（用户指令 > 本文件 > Guide 文档 > 代码惯例）+ 发现矛盾必须停止上报 | 深层原因·无冲突裁决 |
| 1 | **任务分级 L0–L3**，各级对应流程强度；拿不准向上取一级 | 深层原因·无分级；L3 须先批准方案再施工 |
| 2 | **8 条硬边界禁止清单**：Git 写操作 / Docs 外建文档 / 密钥与部署面 / 删范围外文件 / 越权扩大范围 / 臆造事实 / 谎报验证 / 静默降级 | 深层原因·无失效边界 |

| 9–10 | 违规处置；规范自身维护规则（改本文件属 L3，须同步 dev-conventions 摘要） | 防止规范再次腐化 |

**② `Docs/Guide/dev-conventions.md` 同步**

- 「强制规范」小节标题由 **`（来自 CLAUDE.md）`** 改为 **`（摘要）`** —— 原引用来源 `CLAUDE.md` **在仓库中根本不存在**（`find -iname CLAUDE.md` 无结果），属长期错误指向；现明确标注权威版本为 `Docs/Force_command.md`，并声明"冲突时以其为准"。
- 6 条摘要扩为 11 条，与新规范逐条对齐（新增：任务分级、版本号三处、硬边界、不臆造不谎报、配置 key 登记顺序）。
- 「提交前检查」小节补入两个门禁脚本命令与"非零退出必须修到通过"的要求（原小节只有 `docker-compose up`，无任何门禁信息）。

### 关键设计决策

- **历史日志目录不迁移**：`26-06/06-27/`、`26-07-26/` 等旧写法保持原样，因 CHANGELOG 中已有大量指向这些路径的链接，迁移将造成批量死链。规范中显式声明"旧写法不迁移，新建一律按新格式"，用**新增合规**而非**存量重整**收敛漂移。
- **分级而非一刀切**：L1 微改免独立日志（但必须进交接块），把仪式成本投放到真正需要可追溯的 L2/L3 上，避免规范因不可执行而被整体绕过。
- **本次任务即首个样例**：本日志与随后的版本号/CHANGELOG/门禁/交接块，完整走了一遍新规范的 L3 流程，可作为后续会话的参照实例。

## 6. 遗留与风险

- **`dev-conventions.md` 尾部存在游离段落**（「✅ 使用者收益」「🔄 兼容性说明」）：内容是某次版本发布说明的残留，与"开发约定"主题无关，按 SSOT 应归入 CHANGELOG。**本次未删除**——按新规范第 2 节第 4 条"禁止删除本次任务范围外的内容"，此项列出待用户批准后处理。
- **`Docs/Example_prompt.md`（43 行）未纳入本次治理**：与 Force_command 存在潜在职责重叠，建议后续单独评估是合并、改为"提示词模板库"，还是废弃。
- **规范的效力依赖每次会话完整读取本文件**：用户已选择不新建根 `CLAUDE.md` 自动加载入口，因此仍需在会话开始时手动引用 `Docs/Force_command.md`。若后续发现遗漏率高，可重新考虑该入口方案。
- **门禁脚本覆盖面有限**：`CheckStructureTree.py` 按文件名（非全路径）比对，同名文件视为一个条目；只覆盖 `frontend/src`，后端结构树无对应门禁。规范中的 DoD 依赖人工核对后端树。
