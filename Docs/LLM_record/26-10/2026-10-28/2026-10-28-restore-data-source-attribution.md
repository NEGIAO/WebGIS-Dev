## 一、问题分析

### 1.1 核心症状

建筑抓取能力在三处露出的是匿名标识：

| 位置 | 匿名写法（HEAD） |
|---|---|
| 抓取面板三个 tab | `建筑1` / `建筑2` / `矢量瓦片` |
| 面板描述与错误提示 | 「建筑1：无需单独凭证…」「未配置建筑2凭证」「当前矢量瓦片凭证缺少矢量瓦片权限」 |
| 落地页功能卡 | 已含真实名，但未说明「谁做了全量、谁只做了建筑层」 |
| README 功能行 | 「**腾讯 / 高德 / 天地图** 三类矢量瓦片数据源：腾讯、高德抓建筑轮廓与楼高…」——未点明只到建筑层级 |

### 1.2 根本原因

历史上有一次**合规强化**（`CHANGELOG` 中「建筑抓取合规强化与匿名展示」）：把前端展示由具体来源名改成「建筑1 / 建筑2 / 矢量瓦片」，同时加了勾选确认与会话级弹窗。动机是避免直接点名商业平台带来的合规风险。

### 1.3 现状与需求

三个数据源本身都是公开可访问的矢量瓦片服务，分属商业平台与国家平台：

| 界面标签 | 真实来源 | 本项目实现程度 |
|---|---|---|
| 腾讯 | 腾讯地图（腾讯位置服务） | 仅建筑层级（CE） |
| 高德 | 高德地图（高德开放平台） | 仅建筑层级（CE） |
| 天地图 | 天地图（国家地理信息公共服务平台） | 全量 12 类图层 |

三者共用同一套瓦片解码与几何装配链路，差别只在图层过滤与凭证策略。因此「谁做了全量」是**实现进度**问题，不是能力边界问题——放开图层过滤即可把全量解析扩展到腾讯与高德。

用户要求：恢复真实署名，并把上述实现边界写清楚（既不失实，也不夸大）。

## 三、修改原因

- 匿名标识让用户无法判断数据能不能用于自己的场景（不同平台的授权条款差异很大），也让「为什么天地图有 12 层、另外两个只有建筑」变成黑盒。
- 只写「三类数据源」而不写实现程度，等于把「我只做了建筑层」藏起来，与「诚实说明能力边界」的原则相悖。
- 三源共用一套链路这件事值得明说：它既是技术事实，也是「别人可以在此基础上扩展全量解析」的依据。

## 四、影响范围

落地页功能卡、建筑抓取面板的三段来源描述、README 功能表与合规声明、版本摘要与 CHANGELOG。无逻辑改动，无接口/配置变更。

## 五、解决方案

采用「**真实来源 + 实现程度**」双列表达，避免两种失真：

| 写法 | 问题 |
|---|---|
| 只写「三类数据源」 | 掩盖了只做建筑层的事实 |
| 写成「支持三源全量解析」 | 夸大能力，天地图之外的 12 类并未实现 |

因此文案统一为「谁 + 做到哪一层 + 怎么扩展」，并在 README 合规声明里用表格固化，使 UI、README、CHANGELOG 三处口径一致。
