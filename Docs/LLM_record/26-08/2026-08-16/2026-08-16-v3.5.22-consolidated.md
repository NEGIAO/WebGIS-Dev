## 问题分析

### 核心症状（按功能域）

1. **首屏语言**：全新访客（localStorage 无语言偏好）时，Landing / 登录页默认渲染中文，英语及其它语言用户首屏即错；且语言初始化链路存在两处硬编码默认（`useLocale.js` 与偏好 store），改一处不生效。
2. **语言脏数据**：远端偏好为空的账号登录后语言被折叠回 `zh-CN`；历史脏数据（如 `'fr'`）也被误判为中文；偏好表单草稿占位仍写死 `'zh-CN'`，与「跟随浏览器默认」策略不一致。
3. **注册页导航缺口**：`/register` 页内无返回首页（`/`）入口，只能浏览器后退；`/terms`、`/privacy` 法务页同样无首页出口；注册页品牌区（标题 + 副标题）在常见宽度下被单行截断省略。
4. **第三方登录仅 Google/GitHub**：平台部署在 Hugging Face Space，目标用户高度重合 HF 生态，缺少 Hugging Face OAuth 登录；认证链路的 provider 枚举、配置层、路由 ticket 试探列表、前端三入口（登录按钮 / 账号绑定 / CTA pill）均为双 provider 硬编码。
5. **HF emailVerified 不确定**：HF `whoami-v2` 的 `emailVerified` 字段实机行为未验证——若返回 false，自动注册/绑定会被「缺少已验证邮箱」统一规则拦截，可能误伤 HF 用户。
6. **L3 状态监控手动维护**：新增 L3 密钥后需手动在 4 处同步（启动日志 `masked_summary`、Admin API `_get_l3_env_status`、前端 `L3_STATUS_LABELS`、i18n `admin.envKeys.*`）——本次 HF 即漏加前端映射，监控缺行。
7. **商标图标不标准**：Google 图标为 FA 6.4.0 的旧版（2015 前）单色 G；Hugging Face 图标为 Simple Icons 单色线条笑脸，非官方彩色品牌形象，14~16px 缩放下辨识度低。

### 根本原因

1. 语言 SSOT（`useLocale.js` `normalizeLocaleLanguage`）契约「非 en-us 一律 zh-CN」把「无偏好/不支持」误判为「中文」；偏好 store 的 `DEFAULT_PREFERENCES` 与 bootstrap 链路各自写死 `'zh-CN'`，且 `main.js` bootstrap 会覆盖组件层的任何检测。
2. 语言偏好映射层（`normalizePreferences`）与两个表单组件未区分「未设置偏好」与「显式中文」；`normalizeLocaleLanguage` 的 else 分支恒折叠中文。
3. 注册页头部只有品牌徽标 + 语言切换器，无导航出口；Landing 的「登录 / 注册」按钮是单向链接。
4. OAuth 框架各层（常量 / 配置 / 换 token / profile 拉取 / ticket 试探 / 前端白名单）均为 google/github 显式枚举，新增 provider 需逐点打通；HF token 端点要求 Basic 头认证（与 form 传参不同）需要专门分支。
5. HF `emailVerified` 只反映用户隐私设置（HF 注册强制邮箱验证），与 Google/GitHub 的「verified 字段真实反映验证状态」语义不同，共用严格规则会误拦截。
6. catalog.py 已是 L3 key 权威登记表（`layer: "L3"`），但三个消费方（load / admin / 前端）各自硬编码列举，未以 catalog 元数据驱动。
7. FA 6.4.0（BootCDN）字形为旧版单色；字体图标本质单色，无法表达四色/多色品牌。

### 受影响模块

语言初始化链路（useLocale / 偏好 store / 两个偏好表单）· 注册页与法务页导航（RegisterView / TermsOfService / PrivacyPolicy）· 鉴权后端（oauth / routes / constants）· 配置层（catalog / load / public / admin）· 前端 OAuth 入口（auth.js / RegisterView / SecurityTab / LandingView）· 管理员面板 L3 状态卡 · i18n（core / zh-CN / en-US）· 部署文档（oauth-deployment / configuration / handover / 三份 structure / README / README_EN）· `vite.config.js`（allowedHosts 内网穿透白名单）。

## 修改原因

1. 首屏语言：中文用户看中文、英文（及其它语言）用户看英文是基本可用性预期；用户显式切换或登录偏好依然覆盖检测结果，检测收敛在语言 SSOT 唯一入口，避免 LandingView 单独处理导致的 SSOT 污染。
2. 语言脏数据：消除「非中文语言被误判为中文」的缝隙，localStorage 脏 key / 远端脏数据 / 表单本地归一三链路行为统一。
3. 导航缺口：补齐 LandingView ↔ RegisterView 双向往返闭环；法务页与注册页形成一致的「回首页」出口（V3.5.25 明确记录的遗留）。
4. HF OAuth：平台部署在 HF Space，目标用户高度重合 HF 生态；方案对比选「扩展既有 OAuth 框架」而非新建独立模块（复用 state/ticket/session/绑定全链路，符合单一事实来源）；HF 的 Basic 头 token 认证按官方契约单独实现。
5. HF emailVerified 例外：HF 无未验证邮箱账号，严格规则仅误伤；邮箱归属冲突检查（409）与绑定断言仍生效，不构成账号接管面。
6. L3 监控自动化：catalog 已是权威登记表，三个消费方手动列举必然漂移（本次 HF 前端漏加即实证），改为元数据驱动后零维护。
7. 商标图标：使用官方品牌形象（Google 四色 G 与「Sign in with Google」按钮规范一致；HF 官方彩色 logo 符合品牌识别规范），资源集中 `public/images/` 与既有静态资源策略统一。

## 影响范围

语言初始化链路（首屏全部页面 + 偏好 store + 偏好表单 + 切换器高亮）· 注册页头部导航与品牌区展示、法务页返回行 · 鉴权体系（OAuth 登录/自动注册/绑定/解绑全链路 + HF emailVerified 例外；Google/GitHub 行为不变）· 配置层（新增 6 个 key：4 L1 + 2 L3 绝密；`status_label`/`status_exclude` 为 catalog 元数据字段，非 env key）· 管理员 L3 状态卡片与启动日志 `[L3]` 摘要（8 → 9 组，显示名从 i18n 中文变为 catalog 英文 label）· 前端 OAuth 三入口视觉与交互 · 部署文档（HF Secrets 需新增 2 个 key）· dev server 允许 Host 白名单。数据库零变更。

## 遗留与风险

- ⚠️ **HF emailVerified 实机未验证**：代码语义按「HF 注册强制邮箱验证」信任模型确定；若实机发现 HF 存在未验证邮箱账号，需回退严格规则并另行评估。
- ⚠️ **HF 官方 SVG 未实机渲染**：`hf-logo.svg` 源自官方 brand-assets 且结构完整，仍以用户实机验收为准。
- **面板显示名英文化**：L3 状态卡显示名从 i18n 中文变为 catalog 英文 label（`SMTP`、`Google OAuth`、`SUPABASE`），语义不变、与日志格式统一；如需中文需在 catalog label 侧处理（不引入，避免双维护）。
- **Google 渐变版新 G 未跟进**：2025-09 发布，本次采用登录按钮规范基准的标准四色版；未来替换同尺寸 SVG 即可。
- **FA 6.4.0 无 HF 品牌字形**：升级 FA 7.x 后可换 `fa-brands fa-hugging-face`（当前用官方彩色 SVG，无需依赖升级）。
- **`agentMapPresets.js:4` 注释残留旧编号「V3.5.28」**：该文件非本次暂存范围（已提交文件），其注释沿用 2026-08-15 旧增量编号，与新版本体系不一致，未擅自修改，记入待办观察。
- **vite `allowedHosts` 含 `negiao.cn` 子域**：dev server 仅本地运行，无生产安全影响；注意该白名单仅为开发便利。
- **第三方 HF 端点无 SLA**：端点变更需同步 catalog 默认值（.env.example 可覆盖）。
