## 一、Agent Chat 配额扣费时序修复（核心）

### 问题分析

**核心症状**：

1. Chat 对话（后端代理模式）每发一条消息，配额被扣 1（依赖层）**又**按 token 扣一次（handler 层），形成双重扣费。
2. 上游 LLM 调用失败/超时时，依赖层已扣的 1 个额度**不会退还**——失败也扣费。
3. 个人 Key 直连模式（`/chat/proxy`）docstring 声明「不消耗平台配额」，但依赖层实际每次扣 1（失败也扣），与文档矛盾。
4. 默认 AI 模式（`/chat/default-proxy`）固定扣 1（不按 token），且失败也扣。
5. 只读状态端点（`/chat/config`、`/models`、`/user-config`）每次调用也扣 1，刷新按钮/切 tab 越刷越扣。

**根本原因**：三个功能端点与四个只读端点都使用了**会消耗额度**的依赖 `require_api_access_or_guest`（每次调用先 `_consume_api_quota_sync(cost=1)` 再进业务逻辑）。功能端点成功后还会再按 token 扣 `agent_cost`，于是「依赖层 cost=1 + handler agent_cost」双重扣费；而依赖层扣费发生在 handler 之前，上游失败时已扣的 1 无法回滚。

**受影响模块**：

- 配额系统（`api/auth/quota.py`、`api/auth/dependencies.py`）
- Agent Chat 路由（`api/agent_chat/routes.py`）
- 前端 Chat 面板（`ChatPanelContent.vue`、`ChatServiceStatus.vue`、`useChatAgentConfig.js`）

### 候选方案对比

| 方案 | 说明 | 结论 |
|---|---|---|
| A. 依赖层不扣费 + handler 成功后按 token 扣费 | 抽出鉴权核心 `_authenticate_login_or_guest`，新增 `require_api_access_or_guest_noconsume`（认证但不消耗配额）；功能端点保留只读配额预检（429）+ 上游成功后才 `_consume_api_quota_sync(agent_cost)`；个人 Key 端点完全不扣 | ✅ 选定：彻底符合「只有真正成功调用了相关功能才扣除额度」，且扣费函数本身原子 + 超限封顶，杜绝重复扣 |
| B. 保留依赖层扣费，仅去掉 handler 扣费 | 仍会在失败时扣 1，且个人 Key 直连继续违背「不消耗平台配额」docstring | 否决 |
| C. 在依赖层做「扣费前检查、成功后扣」 | 改动鉴权核心依赖语义，波及所有使用方 | 否决 |

### 修改内容

**`/chat/completions`（后端代理模式主端点）**

- 依赖 `require_api_access_or_guest` → `require_api_access_or_guest_noconsume`。
- handler 中原有只读配额预检保留（快照 `remaining <= 0` → 429，不消耗）；上游成功后按 token 折算 `agent_cost` 并 `_consume_api_quota_sync`。
- 效果：单次成功只扣 `agent_cost`；上游失败/超时不扣；配额只剩 1 时也可正常用掉。

**`/chat/default-proxy`（默认 AI 专属 Key 代理）**

- 依赖 → `require_api_access_or_guest_noconsume`；新增与 `/chat/completions` 一致的只读配额预检（429）。
- 上游成功后按 token 折算 `agent_cost` 并扣费，响应新增 `quota` / `cost` 字段。
- 效果：从「每次固定扣 1（失败也扣）」变为「仅成功、按实际 token 折算」。

**`/chat/proxy`（用户个人 API Key 直连）**

- 依赖 → `require_api_access_or_guest_noconsume`，兑现 docstring「不消耗平台配额」。

**四个只读状态端点**（`/chat/config`、`/user-config`、`/models`、`update_user_model_preference`）

- 依赖改 `require_api_access_or_guest_noconsume`：消除 V3.5.15「`require_login` 造成游客访问回归」的同时，保留「认证但不扣额」的目标。游客（非分享模式）恢复可访问。

**`quota_subject` 漏传修复（追加）**

- 本版本新增的两处聊天端点扣费调用漏传 `quota_subject`，函数内部回退用 `username` 作主体，与预检/展示用的 `resolve_quota_subject` 不一致：**游客**扣费写进 `user_N` 行，预检/展示却读 `guest_uid` 行——扣的额度永远不反映到展示余额，游客配额也永远不被预检拦截（实为「无限额度」隐患）。
- 修复：`/chat/completions`、`/chat/default-proxy` 的扣费调用补传 `quota_subject`（两个 handler 均已用 `resolve_quota_subject(username, role, session.get("guest_uid"))` 算好，直接复用）。

**`dependencies.py` 重构**

- 抽出鉴权核心 `_authenticate_login_or_guest`（登录 token 有效则用登录身份，否则创建 guest session，不消耗配额）。
- `require_api_access_or_guest` = 认证核心 + `_consume_api_quota_sync(cost=1)`（保留既有语义，供天气/搜索等仍按调用计费的端点使用）。
- 新增 `require_api_access_or_guest_noconsume` = 仅认证核心，供只读状态端点与「成功后扣费」端点使用。
- `api/auth/__init__.py` 导出新依赖。

## 四、统一配额池超限策略与统计

### 问题分析

**核心症状**：`_consume_api_quota_sync` 超限时执行**整单回滚 + allowed=False**。在「先调用后扣费」的 Agent 对话路径上，路由层不拦截返回值（上游已成功、答案已生成），结果余额原封不动、服务白送，用户可反复发起超限请求绕过配额。此外管理员面板「用户统计」页只展示调用次数明细，无法看到统一配额池的消耗。

### 修改内容

- `backend/api/auth/quota.py`：超限策略由「整单回滚」改为「**封顶**为每日限额（`calls = daily_limit`），只扣到上限，不做整单回滚」。封顶后 `used=limit / remaining=0`：本次请求正常交付，但**下一次请求**会被各端点的配额预检以 429 拦截，堵住「余额不足仍可继续请求」的绕过漏洞。
- `backend/api/agent_chat/routes.py`：两处扣费点补注释说明「不拦截 allowed=False 的原因」（上游已成功、正常交付，超限由下次预检拦截）。
- `backend/api/api_management.py`：新增 `GET /api-management/usage/quota-by-user` 端点 + `_get_quota_usage_by_user_sync`，按用户聚合 `api_usage_daily` 配额池消耗（总消耗 / 今日消耗 / 活跃天数 / 最后使用时间）。
- `frontend/src/domains/common/user/components/ApiManagementPanel.vue`：「用户统计」页签改读 `apiAdminQuotaUsageByUser`，列改为「总消耗配额 / 今日消耗 / 活跃天数 / 最后使用」，标题改「用户配额消耗统计」。
- `frontend/src/api/backend/admin.js`：新增 `apiAdminQuotaUsageByUser`。

## 六、双向保活机制与运维

### 问题分析

Hugging Face Spaces 在 24 小时无外部访问后自动休眠，首次访问有 30–60 秒冷启动延迟。本平台两个 HF Space（WebGIS 后端 + New API）通过**双向互探活**保持活跃，避免休眠。此前的保活实现无接收日志、uvicorn 访问日志噪音大（外部扫描器 404 淹没保活日志）。

### 修改内容

- `backend/api/keepalive.py`（新模块）：
  - **接收端**（公开无鉴权）：`POST /api/heartbeat`（接收 JSON 心跳包）、`GET /api/heartbeat`、`GET /api/keepalive/ping`（兼容探活），新增 `_log_keepalive` 统一记录接收日志。
  - **发送端**：asyncio 后台任务每 3~6 分钟（随机 180~360s，严禁死定时）GET 对端 `https://negiao-newapi.hf.space/api/status`，请求头拟人化（Chrome/Edge/Firefox 多版本 UA + Accept + Accept-Language 随机轮换），复用 `app.state.http_client` 连接池。
  - `start_keepalive_sender(app)` 供 lifespan 启动后台任务。
- `backend/app.py`（Code Review 修复）：`keepalive_router` 曾被**重复注册**（line 354 proxy 之前 + line 411 末尾），删除后者，仅保留 proxy 之前的注册（该处注释明确要求「必须在 proxy 之前，避免被 /api/* 通配拦截」），消除 OpenAPI 重复 operation 与冗余注册。
- `backend/Dockerfile`：uvicorn 增加 `--no-access-log`，关闭请求访问日志，避免外部扫描器 404 噪音淹没保活日志。
- `Docs/Architecture/keepalive-hf-space.md`（新文档）：双向保活架构（Mermaid 图：三层冗余——asyncio 主发送端 + cron 兜底 + 对端互保）、公开探活接口表。

## 七、错误处理重构（console.error → message + detail_code 透传）

### 问题分析

**核心症状**：

1. 前端 38 个文件中散布 65 处 `console.error`，控制台噪音大，且错误只停留在开发者工具，用户侧无提示。
2. 前端 429/401 特判分支（`GUEST_NO_TOKEN` / `EMAIL_BINDING_REQUIRED` / `DOWNLOAD_QUOTA_INSUFFICIENT`）失效：`app.py` 全局异常处理器把 dict 型 `detail` 展开成纯字符串，`data.detail` 永远不是 dict，`detail_code` 无法透传；前端 `client.js` 也没有从 `data.detail_code` 兜底提取。
3. 暂存区代码新增大量 `catch (error)` 但 console.error 注释化后 `error` 无引用，触发 `@typescript-eslint/no-unused-vars`（17 处）。

### 修改内容

- **结构化错误透传（后端）**：`backend/app.py` 全局 `HTTPException` 处理器新增 dict-detail 分支：保留业务 `code` → 输出独立 `detail_code` 字段 + 透传 `message`（不再 `str()` 破坏结构化数据）。
- **结构化错误提取（前端）**：`frontend/src/api/backend/client.js` 拦截器补 `data.detail_code` / `data.message` 兜底提取；`parseBlobError` 补 `json?.detail_code`；错误 toast 格式改为 `"401，登录状态已失效"` 这类「状态码 + 结构化 message」拼接。
- **console.error → message 重构（65 处）**：
  - **A/B 类（只注释，不重复弹窗）**：所在 catch 已有相邻 message toast，或调用方/拦截器/上游已 toast —— 只注释原行保留可读信息（`CesiumContainer.vue`、`TOCPanel.vue`、`useDownloadStore.ts`×6、`useBasemapSwipe.js`、`BusPlannerPanel.vue`、`DrivingPlannerPanel.vue`、`useSpatialAnalysis.js`、`useMapSearchAndCoordinateInput.js`、`AmapAoiInjectDialog.vue`、`locationSearch.js` 等）。
  - **C 类（注释 + 补 message toast）**：错误路径无任何用户提示 —— 注释原行并新增 `message.error/warning`，必要时新增 `import { useMessage }`：`useStartupViewResolver.js`、`auth.js`（访客令牌注入失败）、`MagicCursor.vue`、`LogMonitor.vue`（复制失败）、`TOCTreeItem.vue`、`basemapProviderFactory.ts`（懒调用）、`kmlStyleParser.js`、`shpParser.ts`、`useLayerDataImport.js`、`useShallowWater.js`、`useCesiumModelManager.js`、`useUserLocation.js`。
  - **Vendored / GPU / DEV-only（只注释）**：`cloud/lib/*`（ShadowPass/ShadowResolvePass/ThreeGeospatialPipeline/loadBinThreeGeospatial）、`wind/index.mjs`、`GeoWTFS.js`（vendored 地形 Provider）、`useMapSwipeTest.ts` 等，由 orchestrator 兜底 toast。
  - `useMessage` 为全局单例（不依赖组件上下文），`auth.js`/解析器/Provider 等非组件调用安全。
- **ESLint 清理（17 处归零）**：未使用 catch 参数按 `^_` 约定重命名（`error→_error`/`err→_err`/`e→_e`，13 处 / 10 文件）；`.catch((err)` 与 `createGLProgram` 的 `label` 参数同步处理；`useSharedResourceLoader.ts` 删死变量 `message` 并移除级联暴露的 `no-useless-catch` try/catch 包裹（错误自然向上传播）；`playerController.ts` 移除裸重抛 try/catch（`Model.fromGltfAsync` 失败直接向上抛给 `usePlayerController` 的 `message.error` 提示）。
- `CheckConfigRegistry.py`：后端扫描排除目录新增 `tests`（单元测试为验证 env 加载需直接操作 `os.environ`，属测试写法而非业务代码裸读，B1 规则按「业务代码」意图对齐）。

## 修改原因

用户要求「刷新面板等不消耗额度的，只有真正成功调用了相关功能才扣除额度」。依赖层扣费是历史遗留的错误时序：让只读端点和失败请求都产生扣费副作用，并在功能端点造成双重扣费。本次将扣费职责收敛到「上游真正成功之后」这一唯一时点，并统一配额池超限策略、补齐统计与运维观测，使记账-展示-监控闭环一致。

## 影响范围

- **Agent 配额记账**：三个聊天端点的扣费行为（仅成功、按 token）；只读端点不再扣费。
- **配额池**：超限策略由「回滚」改「封顶」（影响所有走统一配额池的操作：API 调用 / Agent / 下载）。
- **前端 Chat 面板**：默认 AI / 后端代理模式展示用户自身额度与本次消耗；额度耗尽红色警示 + toast + 发送拦截。
- **管理员面板**：新增「Agent 配额折算」配置；「用户统计」改为配额池消耗统计。

## 遗留与风险

- **超限封顶的时序语义**：预检与扣费之间存在极窄 TOCTOU 窗口。若并发请求在预检后恰好耗尽额度，`_consume_api_quota_sync` 返回 `allowed: False` 并**封顶到限额**（不回滚），本次回复仍交付用户，但下一次请求会被 429 拦截——属有意的设计取舍（避免服务白送），无需加锁。
- **默认 AI 模式**：前端 `quotaExhausted` 已按「默认 AI/后端代理消耗用户额度」对齐；若需在默认 AI 模式展示个人额度明细而非仅额度剩余，属后续 UI 增强。
- **硬编码对端 URL**：`keepalive.py` 中 `PEER_URL`（New API HF Space）为硬编码，后续如需环境变量化可纳入配置登记流程。
- **`AGENT_TOKENS_PER_UNIT` env 为登记/兜底**：运行时值以 system_config 数据库为准（与 `DOWNLOAD_TILES_PER_UNIT` 同款既有模式）。
- **已删除的中间版本日志**：本批次合并前存在的 9 个分主题日志（对应 V3.5.14~V3.5.22 中间版本号）已并入本综合日志并删除，CHANGELOG 仅保留本条目，避免版本号互相矛盾。
